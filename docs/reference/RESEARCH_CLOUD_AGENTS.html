Cloud agents research

Decided 2026-11-25: Flockr runs on Cloudflare through platform adapters (ADRs 0017 and 0018, diagram C4_CLOUDFLARE_NATIVE.html); coding agents are ADR 0019 (proposed). Build order

  1. Docker sandbox adapter on the VPS: create, run, files, delete, with a time limit and disk cap (ADR 0007).
  2. Cloud runner: the Claude Code adapter started inside a sandbox instead of on the Mac.
  3. GitHub App flow: clone, work-in-progress commits, push, open the pull request.
  4. Pi Durable agents for routines and triage.
  5. Blaxel adapter for overflow, with keepAlive during runs, once parallel tasks outgrow the VPS.
  6. Later: run the same 10 coding tasks through Pi Durable with Blaxel tools; move coding over if quality is close.

ADRs this would need

  • Blaxel as the overflow sandbox adapter after Docker, E2B kept as fallback (extends 0007).
  • Coding agents run Claude Code inside a VM; supersedes 0008 for coding agents only (0008 puts coding-agent state in the sandbox volume and makes Pi Durable the default harness).

2. How the parts talk

  • Agents never talk directly. Every agent, cloud or client (Claude Code or Codex on a Mac, a hosted bot over MCP), is a member; it posts to threads and its runner wakes it on mentions and assignments.
  • Example: Claude Code on the Mac posts @builder write tests for branch flockr/830; the cloud runner wakes builder, which pulls the branch into a Blaxel VM, pushes tests and replies @claude tests added, 2 failing; the Mac runner resumes Claude's session with that reply.
  • Ways to work together: mentions, task hand-off and dependencies, and a shared GitHub branch.
  • Watching a cloud agent: follow its stream in the thread or in a Herdr pane (fc watch, still to build). Open a terminal into the box (bl connect sandbox <name>) only to debug, or to see Claude Code's own screen when it runs interactively.

  • agentOS is not enough for coding: its own docs list no native binaries, no Go, Rust or C++ toolchains, no Docker, no browsers, no file watching. Edits and git work; bun test and Vite builds do not. Rivet's answer is to mount a full sandbox on demand.
  • Blaxel vs E2B for Pi plus tools: a 30-minute task with 5 minutes of tool work in 20 bursts bills about 6.7 minutes on Blaxel (about 0.02 USD) and 30 minutes on E2B (about 0.08 USD). At 1,000 tasks a day, about 20 USD against 83 USD.
  • Blaxel vs E2B for Claude Code inside the box: the same. The box must stay awake while Claude waits on the model, so both bill the whole run. Blaxel still sleeps between turns and tasks.
  • Blaxel vs Cloudflare: Cloudflare is not more expensive per awake hour. Its gaps are slower container starts and files-only snapshots. With the brain already in Durable Objects, Cloudflare Computer plus Containers is the better fit; Flockr stays off Cloudflare (ADR 0001), so Blaxel fits Flockr's overflow.
  • Bare metal or VM: a Hetzner Cloud VM for the board and runner. Bare metal (from about 63 EUR a month at auction, always KVM) only once sandboxes are self-hosted.

Blaxel test, 2026-11-25

  • Key stored in Infisical as BL_API_KEY. SDK @blaxel/core 0.3.41. Script kept outside the repo.
  • Box from blaxel/base-image:latest (Alpine, Node 24, git 2.52) ready in 1.9 s. npm install -g @anthropic-ai/claude-code in 4 s (Claude Code 2.1.332). Cloned simonbalfe/flockr and branched in 1 s.
  • Claude Code with the stored subscription token stopped at "You've hit your weekly limit". No pull request yet. Rerun after the reset, or with an API key.
  • Found: a running command does not keep a Blaxel box awake unless the process is started with keepAlive: true (default 600 s timeout; timeout: 0 for none). Without it the box can sleep mid-run.
  • Sandboxes run as root by default; Claude Code refuses --dangerously-skip-permissions as root. Non-root users need Blaxel's Carbon servers (default for new workspaces in us-pdx-1 and us-was-1). The test used --permission-mode acceptEdits with a tool allow-list instead.

7. Rivet: not now

  • What it is: Apache-2.0 actors (an addressable object with its own SQLite) running inside your Node or Bun process; a self-hostable Durable Objects. @rivet-dev/pi runs Pi Durable in an actor (beta) with sandbox adapters for agentOS, E2B, Daytona, Freestyle and Docker.
  • 3.0 storage: each actor's SQLite lives in a durable volume; recent writes sit on the engine instances' disks (acknowledged when most have them) and the S3 or R2 bucket holds "the durable copy of every volume". S3 is the only outside dependency, replacing Postgres or FoundationDB plus NATS in 2.x.
  • Production asks for 3 engine instances on separate machines with 100 GB disks each; one instance is fine to try, at the risk of losing writes not yet in the bucket. Bucket restore was not yet validated for 3.0.
  • Why not now: Flockr already provides what Rivet adds (members as addresses, wake on events, live streams); Pi Durable is crash-safe on a plain file; the board must stay on Postgres anyway. Rivet earns its place when one VPS is not enough or for hosted multi-team Flockr. 3.0 over 2.x if adopted.
  • Cheapest hosting if adopted: Hetzner servers plus R2 (no egress fees). Alchemy deploys Rivet to Hetzner in one command (Rivet changelog, 2026-11-24).

8. Other options looked at

  • Turso: SQLite with a server (libSQL, MIT, self-hostable sqld), replicas and Turso Sync; concurrent writes are a preview and were slower than SQLite under 8 writers in 2026-09. It adds no LISTEN/NOTIFY, row locks or job queue. Not needed: Postgres covers the board and Litestream covers agent files. Supabase is acquiring Turso.
  • Flue: Pi-based framework (Astro team) with channels and a durable event log; overlaps with what Flockr owns. Worth porting two ideas: one settled event per task with its outcome, and token cost per turn.
  • Eve, Mastra, Vercel AI SDK, TanStack AI, Google ADK for Go: frameworks or model libraries one layer up; none replaces the board or the runner.
  • Herdr on a VPS: the cheapest way to get load off the Mac now (same Claude Code workers and subscription, panes over remote attach), without crash recovery or triggers.
  • Similar products: agentes.chat, Buzz, open-tag, agentslack and Switch all use Postgres; only single-user local tools (Dusk bot, Vibe Kanban, MCP Agent Mail) use SQLite.
